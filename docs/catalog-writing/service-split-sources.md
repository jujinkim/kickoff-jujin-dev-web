## Authored comparison fixture

One team initially owns a reading application with Catalog, Library and Billing. All release units begin at v1; A17 has no tag. The change adds Library tag support without changing Billing behavior. Monolith and modular monolith ship one app v2. Microservices ship only Library v2 under a compatible contract, leaving Catalog and Billing at v1; no one-team-per-service requirement is asserted.

After release, Library reads A17 from Catalog before storing the literal tag `travel`. This is an in-process call in the two monoliths and a network request in the microservices example. A lookup error/timeout before writing leaves no tag, reports failure and allows retry after recovery. This deliberately bounded outcome is not a claim about ambiguous write timeouts, automatic retries or distributed transactions. Assigning the same tag again is an illustrative assignment policy, not a property supplied by architecture.

The plain monolith example has one application-owned database and leaves internal modularity unspecified. The modular monolith example has a shared database with module-owned tables, accessed only through module APIs. These ownership rules require enforcement, not just folders. Microservices show service-owned stores with no direct cross-service table access; boxes do not mandate separate database machines or promise that downstream failures cannot propagate. Logical layers and ports can exist inside any release unit.

Static diagrams show before/after artifact versions, ownership and the success/failure paths together. They do not run an application, database or deployment. Three English overviews were cross-reviewed for deployment coupling, local/remote calls, version semantics and conditional tradeoffs before translation. No product version, price, performance or legal claims are introduced.
