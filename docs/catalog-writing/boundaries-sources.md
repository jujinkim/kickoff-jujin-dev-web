## Shared editorial fixture

SaveArticle(R1, A17), initially unsaved, executes in one process. HTTP or CLI is the entry; memory or an embedded database is the storage alternative. Empty IDs are rejected before writing. Successful save returns Saved and one entry; repetition retains one. A failure explicitly occurring before writing retains zero, followed by retry after correction. These outcomes are independently traced examples from an empty store, not claims that architecture automatically provides idempotency or resolves uncertain write outcomes. Switching storage denotes alternative implementations, not migration of saved data.

Solid arrows label source imports; dashed arrows label runtime calls; dotted enclosures label a single process. Layered imports and calls descend in the chosen closed-layer design. Hexagonal storage adapters depend on the application-owned port. Clean architecture keeps SaveRepository with application contracts and SavedArticle validation in the domain; only plain IDs/results cross external boundaries. The three approaches can overlap.
