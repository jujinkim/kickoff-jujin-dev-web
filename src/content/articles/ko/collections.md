## 왜 필요한가

저장한 책 목록에 중복이 생기고 순서가 바뀌거나, 제목을 수정한 뒤 항목을 찾지 못합니다. 익숙한 자료구조를 고르는 것만으로는 이런 모호함이 해결되지 않습니다. 무엇을 같은 책으로 볼지, 순서가 중요한지, 반복 동작이 무슨 뜻인지 먼저 정해야 합니다. 저장 표현은 이 규칙을 지키기 위해 선택합니다.

## 어떻게 해결하는가

1. 식별자 몇 개로 화면 동작을 설명합니다. A17을 저장하고 B04를 저장한 뒤 A17을 다시 저장합니다. 합의한 결과가 처음 넣은 순서의 두 항목이라고 가정합니다. 제목은 표시할 글자이고, 고유 ID는 이름이 바뀌거나 제목이 같은 책이 있어도 대상을 구별하는 기준입니다. 표시와 정체성을 섞지 않습니다.
2. 필요한 작업을 나열합니다. 순서대로 읽기, ID로 찾기, 포함 여부 확인, 구매 수량 세기는 서로 다릅니다. 중복이 수량을 뜻한다면 임의로 없애면 안 됩니다. 책 두 권이 담긴 장바구니와 중복 없는 북마크는 같은 요구사항이 아닙니다. 먼저 사용자가 기대하는 결과를 예시로 확인합니다.
3. AI가 초기 표현을 고르게 합니다. 배열은 순서 있는 항목을 담고, 맵은 키와 값을 연결하며, 집합은 중복 없는 포함 관계를 다룹니다. JavaScript의 맵과 집합은 삽입 순서로 순회하지만 모든 언어의 컬렉션이 그렇다고 가정해서는 안 됩니다. 실제로 사용할 언어의 규칙을 확인해야 합니다.
4. 동일성도 시험합니다. 같은 책 ID를 담아도 따로 만든 JavaScript 객체 둘은 서로 다른 키입니다. 제품에서 고유 ID로 같은 대상을 판단한다면 조회 키에도 그 ID를 씁니다. 없는 항목을 찾거나 이미 지운 항목을 다시 지웠을 때의 처리도 정합니다. 조회는 늘 성공한다고 가정하지 않습니다.
5. 두 번째 색인은 필요할 때만 둡니다. 순서 목록과 조회용 맵을 함께 유지하면 추가·삭제·수정 때 둘을 맞춰야 합니다. 측정 결과나 필요한 작업이 동기화 비용을 정당화하기 전까지는 하나의 기준 표현으로 시작하는 편이 관리하기 쉽습니다. 빠를 것 같다는 추측만으로 같은 사실을 여러 군데 저장하지 않습니다.

처음의 저장 순서 외에 삭제, 이름 변경, 알 수 없는 ID, 반복 요청도 확인합니다. 새로고침 뒤 데이터가 남는지는 별도로 시험합니다. 메모리 안의 컬렉션은 영구 저장소가 아닙니다. 사용자는 의미 있는 순서와 중복 동작을 결정하고, AI는 합의 안에서 구현을 고르면 됩니다. 내부 컨테이너 이름을 사용자 설문으로 만들 필요는 없습니다.

각 동작 뒤 예상하는 ID 목록을 적으면 최적화를 고르기 전에 순서와 포함 관계의 변화를 눈으로 비교할 수 있습니다.

## 무엇이라 부르는가

이것이 컬렉션의 의미, 즉 순서·키 기반 조회·유일성을 구분하는 작업입니다. 배열·맵·집합은 이 작업을 서로 다르게 지원합니다. [MDN의 키 기반 컬렉션 설명](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Guide/Keyed_collections)에서 JavaScript의 구체적인 규칙을 확인할 수 있습니다. 출발점은 지켜야 할 동작입니다. 최적화는 대표적인 입력으로 측정한 뒤 하며 자료구조에 보편적인 우승 순위가 있는 것은 아닙니다.
