## 목적과 적용 범위

개발 시작 지침 문서, provided by Kickoff by jujin. 지침 버전: v1. 리비전: 3. 갱신일: 2026-09-24. 영어가 원본이며, 한국어·일본어는 원본 리비전 3에 대응합니다.

서비스 아이디어를 합의된 프로젝트 기획으로 구체화합니다. 이 문서는 입력 수집과 기획을, [AI 행동 지침](https://kickoff.jujin.dev/ai/instructions.md)은 결정 주체·권한·근거 규칙을 담당합니다. 시작 시 필수 사이트 문서는 이 두 개뿐입니다. 기존 프로젝트 지침·확정된 결정과 함께 적용합니다. 사용자 언어로 답하고 상위 지침을 우선합니다.

## 1. 서비스 맥락 수집하기

지침 버전·리비전과 두 문서의 열람 여부를 짧게 알립니다. 하나라도 접근할 수 없으면 URL을 밝히고 본문 제공을 요청하거나 재시도합니다. 읽지 못한 규칙을 적용했다고 하지 않으며, 가능한 맥락 수집은 계속합니다.

이미 받은 답은 재사용하고, 빠진 입력을 함께 묻습니다.

- **서비스(앱) 이름:** 사용자가 준 가칭을 쓰거나 미정으로 남깁니다. 확정된 이름을 지어내지 않습니다.
- **서비스 설명:** 누가 사용하고, 어떤 주요 행동을 하며, 어떤 결과를 원하는지 받습니다. 거친 한 문장으로 시작해도 됩니다. 대상·MVP·제외 범위·측정 가능한 성공 조건을 구체화한 뒤 아키텍처를 추천합니다.
- **참고사항:** 우선순위와 알려진 제약을 묻습니다. 기존 시스템·디자인, 연동, 민감한 데이터, 접근성, 예산·일정·팀·플랫폼·운영 중 관련 항목을 다룹니다. ‘없음’·‘아직 모름’도 허용합니다. 빈칸은 제약 없음이 아닌 추가 확인 대상으로 봅니다. 비밀정보는 요구하지 않습니다.

설명은 대화의 출발점이며 완성된 명세가 아닙니다. 후속 질문은 관련 항목끼리 조금씩 묶고, 낯선 용어는 해당 서비스의 예시로 설명합니다.

## 2. 프로젝트의 실제 결정 도출하기

요구사항과 제약에서 필요한 결정 목록을 도출하고 의존 순서대로 다룹니다. 사이트 수록 여부와 관계없이 아키텍처·도구·시각 디자인·운영 방식을 검토합니다. 프로젝트 적합성을 기준으로 동등하게 평가합니다. 카탈로그 분류별 검토표, 전체 색인, 분류마다 하나씩 선택하는 절차는 요구하지 않습니다. 양립 가능한 선택은 함께 쓸 수 있습니다.

사용자가 정할 미결정 항목에는 **직접 선택 / 추천받기 / 해당 범위 위임 / 해당 없음 / 보류**를 제공합니다. 근거 규칙에 따라 목적·대안·장단점·추천을 설명합니다. 사용자가 모르겠다고 하면 일관된 추천 조합을 제안하며, 이를 위임으로 해석하지 않습니다. 보류·해당 없음에는 이유와 재검토 조건을 기록합니다.

카탈로그는 선택적으로 읽는 학습 자료입니다. 사용자가 지정하거나 결정의 이해를 도울 때 특정 글을 참고하며, 인용 전에는 읽습니다. llms.txt·catalog.json·분류 페이지·연결된 모든 글의 조회는 필수가 아닙니다. 선택 자료에 접근하지 못했다는 이유만으로 기획을 중단하지 않습니다. 부족한 근거는 행동 지침에 따라 처리합니다.

## 3. 소프트웨어 경계 계획하기

합의된 프로젝트 선택 안에서 모듈 책임, 의존 방향, 도메인·데이터 소유권, 공개 계약, 외부 경계, 복구 책임을 정합니다. 프로젝트 규모에 맞는 이유를 설명하고 추측에 의한 계층·추상화를 피합니다. SOLID·GRASP의 책임·의존성 원칙을 프로그래밍 방식에 맞게 적용하되, 객체지향이나 특정 아키텍처를 강제하지 않습니다.

입력 검증, 권한, 비밀정보 관리, 데이터 수명, 복구 가능한 실패, 운영 관측을 필요한 만큼 계획합니다. 합의된 예산·중단 시간·복구·운영 책임에서 빌드·테스트·릴리스·호환성·롤백·유지보수 절차를 도출합니다. 검증은 요구사항과 위험 경계에 연결합니다.

## 4. 사용자 경험 계획하기

주요 사용자 흐름, 정보 위계, 탐색 구조, 레이아웃, 서체, 색상·간격, 컴포넌트, 상호작용을 필요한 만큼 정의합니다. 물려받은 디자인 제약을 존중합니다. 초기·로딩·빈 상태·성공·오류·비활성·복구 상태를 포함합니다.

반응형 읽기 순서, 레이블, 키보드 조작, 보이는 포커스, 대비, 대체 텍스트, 동작 감소를 계획합니다. 웹은 WCAG 2.2 AA를 목표로 적용할 검증을 정하고, 네이티브는 플랫폼 지침을 포함합니다. 검증 없이 준수를 선언하지 않습니다. 시각 스타일은 핵심 작업을 지원해야 합니다.

## 5. 기획 제시 후 개발하기

프로젝트 규모에 맞춰 AI가 기획을 작성합니다.

- 입력받은 이름·설명·맥락, 번호가 있는 요구사항, MVP·비목표, 측정 가능한 완료 조건.
- 소프트웨어·디자인 결정과 대안·이유·가정·영향·재검토 조건. 제안·채택·거절·대체·보류 상태, 결정 주체, 정확한 위임 범위.
- 위험·미확정 질문·차단 사항, 의존 순서에 따른 작업 목록, 요구사항에 연결된 검증 계획.
- 지침 버전·리비전과 실제 참고한 자료만 기록. 카탈로그 조회일·글 ID 목록·카탈로그 사본은 필수가 아닙니다.

전체 기획안을 보여주고 확정받습니다. 개발을 막는 선택은 해결하고, 차단하지 않는 보류 항목도 명시합니다. 기획 승인과 명시적인 개발 요청 후 개발합니다. 기존 승인과 개발 권한은 해당 범위 안에서 유효하므로 다시 묻지 않고 실행합니다. 기획이나 기획 위임만으로 개발·배포·공개·지출이 허가되지는 않습니다.

## 6. 함께 개선하기

표현 개선, 빠진 주제, 반례, 번역을 [이슈](https://github.com/jujinkim/kickoff-jujin-dev-web/issues)나 PR로 제안할 수 있습니다. 선택 참고자료인 [기여 지침](https://github.com/jujinkim/kickoff-jujin-dev-web/blob/main/CONTRIBUTING.md)에 예시·시나리오 검토·버전 정책이 있습니다. 이번 출시 전 개선은 v1 리비전 3으로 유지하며, 기존 v1/latest URL과 API schemaVersion 1은 바꾸지 않습니다. 이 문서는 AI를 안내하지만 준수를 보장하지는 않습니다.
